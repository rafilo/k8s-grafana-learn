# Kubernetes monitoring

`kubernetesMetrics.enabled=true` adds real Kubernetes measurements alongside the
Java API metrics. Kubernetes values are collected from the API and kubelet, not
generated by the payment simulator.

## Sources and coverage

| Source | Metrics available |
| --- | --- |
| kube-state-metrics | Pod Ready/phase, container restarts, waiting reasons (CrashLoopBackOff/ImagePullBackOff), last OOMKilled reason |
| kube-state-metrics | Container CPU/memory requests and limits; Deployment/StatefulSet/DaemonSet desired and ready/available replicas |
| kube-state-metrics | Node Ready, MemoryPressure/DiskPressure/PIDPressure, allocatable CPU/memory, HPA current/desired replicas, PVC phases |
| kubelet `/metrics/cadvisor` | Container CPU usage, working-set memory/RSS, CPU throttled periods, Pod network bytes and dropped packets, container filesystem usage/limit where supported |
| Prometheus | `up` for each exporter/node target, scrape duration and sample counts |

The **Kubernetes Runtime Metrics** dashboard in Grafana's **Local Kubernetes Demo**
folder contains 20 panels and a namespace selector. Nodes are cluster-wide;
workload state and stored cAdvisor metrics are scoped to the Helm release namespace.
Java scrape series now also include `namespace`, `pod`, `node`, and `container`.

Kube-state-metrics does not need metrics-server. Host CPU utilization, host disk
I/O, control-plane/etcd metrics, and PVC used bytes are not provided by this setup.
Node allocatable memory is capacity, not actual memory consumption. HPA, PVC,
StatefulSet and DaemonSet panels show no data when no such resources exist.
Runtime-dependent cAdvisor counters can also be absent; no data is not zero.
The last OOMKilled reason may persist after recovery and is not an event count.
Network drops are interface-level observations, not end-to-end packet loss.

## Deploy

Start Docker Desktop Kubernetes, then run from the repository root:

```powershell
helm lint ./charts/production-simulator
helm upgrade --install production-simulator ./charts/production-simulator --namespace monitoring-demo --create-namespace --wait --timeout 3m
kubectl get pods -n monitoring-demo
```

With defaults there are four Pods: two Java replicas, Prometheus, and
kube-state-metrics. The existing checksum annotation rolls Prometheus when its
scrape ConfigMap changes. Grafana automatically reads the new mounted dashboard
JSON; allow its provisioning scan to complete.

This chart pins kube-state-metrics v2.17.0 (built against Kubernetes v1.33 APIs);
the image is configurable using `kubernetesMetrics.kubeStateMetricsImage`.
Validate compatibility with your cluster before using a different version.

## Access scope

Kube-state-metrics gets list/watch access to the selected workload resources in
the release namespace and to nodes cluster-wide. It has no Secret access.
Prometheus retains its namespace Pod discovery Role and gains node discovery and
`get nodes/proxy` for authenticated HTTPS scraping through the API server; the
cluster CA is verified. **`nodes/proxy` is broader than a metrics-only permission**:
Kubernetes RBAC cannot restrict it to `/metrics/cadvisor`. This is intended for
the local demo. In a restricted cluster, use an approved collector or direct
kubelet scraping with suitable certificates and `nodes/metrics` authorization.
Metric relabeling limits stored samples, not authorization to the underlying data.

Disable the proxy collector and its associated cluster permissions with:

```powershell
helm upgrade production-simulator ./charts/production-simulator --namespace monitoring-demo --set kubernetesMetrics.cadvisorEnabled=false --wait
```

Set `kubernetesMetrics.enabled=false` to disable both new collectors and their RBAC.
The dashboard files remain available and will show no data for disabled sources.

## Verification and queries

In Prometheus at `http://localhost:19090`, check Targets for one kube-state-metrics
target and one cAdvisor target per node, all `UP`. Check actual metric presence too;
an exporter can be reachable while its resource watches are failing.

```promql
up{job=~"kube-state-metrics|kubernetes-cadvisor"}
kube_pod_status_ready{namespace="monitoring-demo",condition="true"}
increase(kube_pod_container_status_restarts_total{namespace="monitoring-demo"}[15m])
sum by (pod, container) (rate(container_cpu_usage_seconds_total{job="kubernetes-cadvisor",namespace="monitoring-demo",container!="",container!="POD"}[5m]))
container_memory_working_set_bytes{job="kubernetes-cadvisor",namespace="monitoring-demo",container="app"}
100 * sum by (pod, container) (rate(container_cpu_cfs_throttled_periods_total{namespace="monitoring-demo",container="app"}[5m])) / sum by (pod, container) (rate(container_cpu_cfs_periods_total{namespace="monitoring-demo",container="app"}[5m]))
kube_node_status_condition{condition="Ready",status="true"}
```

If state metrics are missing, inspect kube-state-metrics logs for list/watch
errors. If cAdvisor is down, inspect its Prometheus target error for RBAC, TLS, or
kubelet availability issues. CPU rate panels need at least two scrapes.
